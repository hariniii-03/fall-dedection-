Why it exists

A silent watcher that only speaks up when it matters

A person living or working alone has no automatic way to signal a fall — manual alerting fails exactly when someone is unconscious or too disoriented to act. This device infers state from motion continuously, stays quiet during ordinary activity, and escalates only when it needs to.

What it does

  • Classifies body state in real time from IMU data alone.
  • Gives silent, glanceable Neopixel feedback for every state.
  • Escalates audibly only for dizzy / fall — severity is tellable by sound.
  • Notifies a caregiver over Telegram on a confirmed fall, no action required from the fallen person.
  • Requires a sustained signal before clearing an alarm, to avoid false-clears.

Not included (v1)

No GPS/location in the alert — assumed stationary in one room.
No two-way voice or video — the Telegram message is informational.
No health diagnosis or vital-sign monitoring — motion only.

How it works

Sensor to alert, a second and a half at a time

Model: dense(450→16, ReLU) → dense(16→8, ReLU) → dense(8→5, softmax), trained on raw windowed accel+gyro samples — no DSP/spectral feature extraction. Train accuracy 0.999, validation accuracy 0.963. Firmware runs this as a hand-rolled forward pass, not a TFLite Micro runtime, since the exported model is plain float weight/bias arrays.

Deciding what to do

Confirm fast, alert unconditionally, recover on its own time

A fall always triggers an alert once confirmed — never conditionally on whether the person seems to be recovering. That's a deliberate reversal from an earlier design that waited to see if the alert was still needed.

Normal

Standing / sitting / walking. Silent Neopixel feedback only.

→

Fallen

~4s debounce, timer set once on first fall reading — filters a single noisy frame, can't stretch out.

→

Alarmed

Telegram alert always fires. Continuous tone, pulsing red Neopixel.

→

Recovering

Any sustained non-fall reading. No time limit. Sends "Resolved" on return to Normal.

Dizzy branches off Normal — amber light, intermittent tone, no alert sent.
↩ Relapse, confirmed on hardware: a fresh fall reading during Recovering re-enters Alarmed and sends a new alert.

Telling someone

The alert can't be allowed to freeze the sensor loop

An early version sent the Telegram HTTPS request directly from the state machine — and froze the entire device for seconds at a time while it was in flight. Sending now runs on its own task, on the ESP32-S3's second core.

Core 1

Sampling & classification

Arduino loop() — reads the IMU, windows samples, classifies, drives the state machine and animations. Never blocks.

→fire-and-forget

Core 0

Telegram task

FreeRTOS task, xTaskCreatePinnedToCore. Owns all retry/backoff. Retries indefinitely, independent of state changes.

Confirmed end-to-end on real hardware, twice in a row: fall → alert sent → recovered → resolved message sent → second fall → alert sent again — real Telegram messages received on a phone every time.

What it doesn't do yet

Said plainly, not hidden

Zero missed falls isn't fully met

~11.2% of fall validation samples are still confused with "dizzy" — likely a data-realism issue (handheld mimicked falls vs. a real worn fall's sharper signature) more than a tuning problem.

Occasional false alarms, by design trade-off

~1.2% non-fall→fall misclassification rate. Classifying once per ~1.5s window (not continuously) keeps this to roughly one false alarm every couple of minutes at rest — accepted per the priority: missed falls matter more than false positives.

WiFi connect time is inconsistent

Observed anywhere from ~5s to 90+s after a cold boot. Message delivery still retries indefinitely regardless, but a slow connect delays the alert reaching a phone.
